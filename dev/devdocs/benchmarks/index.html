Benchmarks

This page explains how the package's timings are taken and records measured results, so that every speed figure in these docs can be traced and reproduced. The scripts live in the repository's benchmark/ folder, whose README explains how to run them and how to compare two runs.

The problems

The benchmark times the suspensions that §5.2 of the paper times for its Fig. 2 and Table 3: unit spheres in a periodic cube of side 400 ($a/L = 1/400$) at five volume fractions. They use the settings that §5.2 takes from Tables 1–2 for an error of $\varepsilon = 10^{-4}$: $\Sigma/\Delta x = 1.00$, $M_G = 10$ and $\lambda_\varepsilon = R_c/\Sigma = 5.5$. The remaining setting, $\Sigma/\sigma$, is Table 3's fastest value for each volume fraction. With $\Sigma = \Delta x$ it fixes the grid, $M = L/\Sigma$. The paper does not print its grids, and Table 3 gives $\Sigma/\sigma$ to two figures. For 0.2 % and 0.8 % the grids below are the only ones that reproduce both of Table 3's values. For the other three the rounding also allows nearby grids (for the densest suspension, anything from 489³ to 525³), and the benchmark takes the round sizes:

The number of particles is rounded down, as the paper does (its Table 1 suspension, 8 % at $a/L = 1/150$, has 64,457 particles). For the densest suspension Table 3 prints $R_c/\sigma = 8.1$, a little above $\lambda_\varepsilon \Sigma/\sigma = 7.8$; the benchmark follows $\lambda_\varepsilon = 5.5$ as §5.2 states.

As in the paper, no two particles overlap: each is placed at a random point and kept only if no particle placed before it is closer than one diameter. Each particle carries a random force with every component between −1 and 1, and no torque: like the paper's §5, the benchmark times the mobility from forces to velocities. A fixed random seed means every run, and both precisions, time the same particles.

How the timings are taken

  • One problem at a time. Each problem is set up, warmed up, timed and freed before the next, because the largest problems need gigabytes of memory.
  • Warm-up first. Before a problem is timed it runs, untimed, for at least 50 calls and at least 10 seconds. The first calls of a session are slow while Julia compiles code, and processors and GPUs change their clock speed with their load and temperature. On a GPU, 50 calls of a small problem last only a fraction of a second, and timings taken right after them started up to a third slower than they settled at; ten seconds of continuous calls bring the machine to the steady state that a long simulation runs in.
  • And again before each measurement. Just before its timed calls, each measurement runs its own call, untimed, for one more second. Switching from one kind of call to another changes how hard the processor and GPU work, and they take a moment to adjust: without this second, the first 15 or so timings of a 1.5 ms GPU call came out about 15 % faster than the rest.
  • Exactly 50 timed calls per measurement, one call per timing. Setup is the exception, with 10 timed calls: each takes up to a few seconds, and a simulation sets up once.
  • Median and middle half. Each measurement is summarised by its median (the middle value, which an occasional slow call does not move) and by its middle half. The middle half is the range holding the middle half of the timings, from the 25th to the 75th percentile. A narrow range means steady timings.
  • PTPS, the paper's speed measure (§5.2), is the number of particles divided by the average time of one call.
  • The machine is recorded with the timings: the processor and GPU, the software versions, how busy the processor was, and the GPU's temperature and clock speed at the start and end of each problem.

What is timed

  • The whole call to mobility!: the cost of one application of the operator, paid on every iteration of a resistance solver.
  • The seven steps of the method (paper §4), each on its own, to show where the time goes: wrapping positions into the box, finding each particle's cell, sorting particles by cell, spreading forces onto the grid, the FFT-based Stokes solve, interpolating velocities from the grid, and the correction between nearby pairs.
  • On the GPU: the whole call again with the data already in GPU memory, and the copies between computer memory and the GPU on their own. mobility! copies the positions and forces to the GPU, and the velocities back, on every call so that users never handle GPU arrays; these measurements show what that convenience costs.
  • Setup (FFCMConfig). On the processor it is timed twice, because of FFTW's saved plans. At setup FFTW searches for the fastest way to transform the grid and remembers the answer for the rest of the session, so a repeated setup skips the search. The first measurement makes FFTW forget before every timing; the second lets it remember. On the GPU, the memory and FFT plans of the previous setup are handed back to the GPU before each timing, so every timing reserves its memory and makes its FFT plans from scratch, as a simulation's first setup does.
  • FFT options on the processor: the Stokes solve with quick FFT plans (fft_planning = :estimate) against searched plans (:measure, the default), and with the FFTs split over all Julia threads (fft_threads). These back the advice on the Performance tips page.

Results

Processor

Measured on 2026-11-04 on a server with two Intel Xeon Gold 6242 processors (16 cores each, 64 hardware threads in all) under Linux, with Julia 1.12.6, FFTW 1.10.0 and ForceCouplingMethod 0.1.0, started with julia -t auto: one Julia thread per call except where the FFTs were split over all 64 threads. The two most dilute problems were timed; the denser ones have 4 to 256 times as many particles (on 210³ to 500³ grids) and are too slow on a processor for 50 timed calls of every measurement. The machine was shared with other users' programs (1–10 cores busy on average, this run included). For almost every measurement the middle half of the timings lay within 2 % of the median; the FFTs split over all threads, which compete with other programs for every core, scattered more.

On these grids, searching for FFT plans made the Stokes solve 15–35 % faster, for a one-time search of 0.4–0.8 s, and splitting the FFTs over 64 threads made it 3–6 times faster. For double precision at 0.2 % these figures use the main measurement of the same solve with searched plans (160 ms, in the table of steps above).

Two caveats, both from the machine rather than the code:

  • The same work at two speeds. This server has two processor sockets, each with its own memory, and the operating system decides where a program's memory lives. The double-precision Stokes solve at 0.2 % ran at about 160 ms in the main measurement and about 195 ms in the searched-plans measurement, which does exactly the same work. In an earlier run the main measurement jumped from 160 to 196 ms partway through, while the searched-plans one stayed at 158 ms. Four separate FFT plan searches all gave 157–161 ms, so the plan is not the cause; where the memory sits most likely is. The benchmark does not try to prevent this, because simulations on such a machine see the same.
  • Setup times vary between runs. A setup is faster when it can reuse memory freed earlier in the session, and whether it can depends on what ran before. The repeated setup of the smallest problem took 13 ms in this run and between 10 and 30 ms in earlier ones. The first setup, dominated by FFTW's search, varied by less than 5 %.

The whole call is timed as users see it, with the positions, forces and velocities in computer memory. The paper defines PTPS as the number of particles divided by the average time to apply the mobility matrix (§5.2). Read off its Fig. 2 (the same GPU model, single precision), the peak values range from about 6.6 million PTPS at 0.05 % to about 8.5 million. With the data already on the GPU, ForceCouplingMethod.jl reaches more at 0.2, 0.8 and 12.8 % (9.6, 11.4 and 10.3 million) and less at 0.05 and 3.2 % (5.3 and 7.9 million); at 0.05 % a call takes under 1.5 ms, and the fixed cost of each call weighs most. The paper's figures come from its own code and the software of its time, and Table 3's settings were tuned for that code, so this is only a rough comparison. Double precision is 4 to 5 times slower than single on this card: GeForce cards do double-precision arithmetic far more slowly than single.

Calibration

The times under What it costs were measured on 2026-11-06 on the same server and software, on one Julia thread, with other programs running on the machine. Each is the first call of ForceCouplingMethod.calibrate in a new Julia session, so it includes compiling it, and the time of one call comes from the report it logs. To repeat one, from the repository root with julia --project=benchmark:

using ForceCouplingMethod
include("benchmark/problems.jl")

problem = benchmark_problem("0.05")
Y, F = paper_suspension(Float32, problem)
L = (Float32(BOX), Float32(BOX), Float32(BOX))
seconds = @elapsed settings = ForceCouplingMethod.calibrate(Y; L, F)

The GPU times were measured on 2026-11-08 on one RTX 2080 Ti of the same server, with the software listed for the GPU results above. The five suspensions ran one after another in one Julia session, so only the first includes compiling, here of both calibrate and the GPU kernels in both precisions. The time of one call is the fastest of three rounds taken in turns with nearby grids after the calibration, each round the median of several calls, and the error is measured against a very accurate answer computed afresh. To repeat one, start the session with using CUDA and pass gpu_acceleration = true to calibrate.

The saving from the starting grid was measured the way the test suite checks it, in test/accuracy/test_calibrate.jl: each grid is timed once, and both walks are given the same times, so timing noise can't decide the comparison. Those runs were in Float32 too.
